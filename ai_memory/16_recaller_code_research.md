# 16: Recaller Code, research (2026-10-15)

Research for the second Recaller-family app planned on branch `recaller-v3` (working name "Recaller Code"). It finds the LLM calls in a product's own Python and TypeScript code, shows each workflow's steps on a board, edits the prompts in place, tests them, and ships changes as pull requests. The owner's decisions behind it are in the session notes of 2026-10-15; this file is only the research.

How it was made: one workflow of 9 agents on 2026-10-15. Three market scans (prompt registries, code-first tools, visual workflow tools) and two technical scans (Python, TypeScript/JavaScript) ran in parallel. A skeptical fact-check of each market scan's closest tools followed, then one synthesis. Web sources only; nothing was installed or run. The acquisitions under "Market context" come from the scans and weren't separately fact-checked.

## The brief

### 1. Bottom line
No existing product does all of this. Other tools cover single parts: some find LLM calls in code, some draw them as a graph, and some edit or test prompts after you move them into their own format. We found no tool that edits a prompt in place in your existing code, groups the calls into confirmed workflows, and ships the change as a git commit or PR.

### 2. Closest existing tools
- **Codag** finds LLM calls in many languages and frameworks using Tree-sitter. It draws them as a live graph linked to source lines and includes an MCP server. **What it lacks:** it is read-only, with no editing, testing or git/PR. It also needs a self-hosted backend running Gemini. We could not confirm it is still active in 2026. [repo](https://github.com/michaelzixizhou/codag)
- **blogus** scans for OpenAI and Anthropic calls, then locks and verifies prompts in CI. **What it lacks:** its `fix` command moves prompts into `.prompt` files loaded through `load_prompt()`. It has no workflow view, and its TypeScript support is not documented. [repo](https://github.com/Skelf-Research/blogus)
- **LangGraph Studio** draws the graph from your code and runs and debugs it. **What it lacks:** it only works with LangGraph, it cannot edit prompts in the source, and it has no git or PR flow. [docs](https://docs.langchain.com/oss/python/langgraph/local-server)
- **AgentFlow** (research paper, July 2026) uses static analysis to build a graph of agents, prompts, models and tools across LangChain, CrewAI, LlamaIndex and others. **What it lacks:** it is a research paper only and read-only. It does not cover the Vercel AI SDK or raw SDK and HTTP calls. [arXiv](https://arxiv.org/html/2607.01640)
- **BAML / GitHub Models `.prompt.yml`** keep prompts as files in the repo, with a playground and evals that run on PRs. **What they lack:** you have to move your prompts into their format, and neither has a multi-step workflow view. [BAML](https://docs.boundaryml.com/home), [GitHub](https://github.blog/changelog/2025-05-19-github-models-built-into-your-repository-is-in-public-preview/)
- **PromptLayer / Langfuse / Vellum** offer prompt registries and visual builders. PromptLayer calls its builder "Workflows/Agents". **What they lack:** prompts live in their registry and are fetched at runtime, or are rewritten into Vellum's own node classes. Their workflows are built inside the tool, not read from your code. [PromptLayer](https://docs.promptlayer.com/why-promptlayer/workflows), [Vellum](https://www.vellum.ai/blog/vellum-workflows-sdk-is-generally-available)

Market context: the field is consolidating. ClickHouse bought Langfuse, Mintlify bought Helicone, OpenAI bought Promptfoo, Palo Alto Networks bought Portkey and ServiceNow bought Traceloop. Humanloop shut down. These are reasons to pitch "no runtime dependency, no vendor lock-in".

### 3. Worth borrowing
- **From Codag:** clicking a node jumps to the source line, the graph re-parses as you type, and there is an MCP server for coding agents.
- **From blogus:** a lock file of prompt content hashes and a `verify` command that fails CI when a prompt changes. Our workflow-mapping file can do the same job.
- **From Langfuse:** an aggregated view (steps with the same name merged, with counts) and an expanded view (loops unrolled). Use these for the flow-diagram view of branching workflows.
- **From BAML and the Promptfoo GitHub Action:** test cases kept next to the prompt, and a before/after eval comment on the PR.
- **From security scanners:** export the mapping as a CycloneDX AI-BOM.

### 4. Scanner approach
**Python:** use `web-tree-sitter` with the `tree-sitter-python` WASM grammar. It runs inside Electron with no Python installed and no native rebuilds. Steps:
- **Find calls:** match call sites against a JSON catalog of method names and their prompt arguments (for example `messages.create` → `system` and `messages[].content`, `responses.create` → `instructions` and `input`, `ChatPromptTemplate.from_messages`, CrewAI `Agent`/`Task` and its YAML files). Seed the catalog from the OpenLLMetry and Cisco aibom lists.
- **Follow variables:** build our own index of imports and aliases, module and class constants, and client objects such as `client = Anthropic()`. Trace each prompt argument back through assignments, imports, `+`, implicit concatenation, f-strings, `.format`, `%` formatting, `dedent` and `join`. Follow helper functions one level in, treating their parameters as placeholders.
- **Rewrite:** splice only the text inside each string, keeping its prefix and quote style. In f-strings, edit only the plain-text parts.
- **Optional:** when Python is installed, a LibCST sidecar can resolve names more precisely and run a `compile()` check. Whether LibCST works under Pyodide is **unverified**.

**TypeScript/JavaScript:** use the TypeScript compiler API, pinned to 5.x/6.x. It is pure JS (about 25 MB), so there are no native modules to package or for antivirus to flag, and its positions match JS string indexes. Steps:
- **Pre-filter:** only analyze files that import known LLM packages or contain LLM API URLs.
- **Follow variables:** `getSymbolAtLocation` plus `getAliasedSymbol` follows constants through imports, barrel files, path aliases and object properties. `findReferences` finds every call site that uses a shared constant.
- **Text-file prompts:** `?raw` imports and `readFileSync` files count as one whole-file prompt.
- **Rewrite:** splice edits with `magic-string`. Never re-print the whole file.

**Read-only:**
- `hub.pull` and other registry fetches, environment and database values, prompts built inside loops or several branches
- dynamic callables such as `@agent.instructions`, `@dynamic_prompt` and function-valued `instructions`
- bytes literals, and any code region that fails to parse cleanly

### 5. Top risks
1. **Wrapper functions** (for example `callLLM(prompt)`) hide the real call sites. Treat a function as a wrapper when its parameter reaches a prompt argument, repeat until nothing new is found, and send unclear cases to Claude for the user to confirm.
2. **Corrupting a file.** Three ways this can happen: tree-sitter gives UTF-8 byte positions while JS strings use UTF-16, escaping is wrong, or a `{}` is confused between an f-string expression and a LangChain/mustache variable. To prevent it:
   - Splice on a Buffer, not a JS string.
   - Show code expressions and template variables as different-looking chips.
   - Re-parse after each edit and check that the string's value equals what the user typed; cancel the write if it doesn't.
   - Test with emoji and non-English prompts.
3. **Shared constants** silently change other workflows. Warn with "used by N prompts" before saving.
4. **API churn:** for example `create_react_agent` became `create_agent`, the Vercel AI SDK went from v4 to v6, and LlamaIndex.TS and google-genai renamed things. Keep the catalog as versioned data that can be updated without an app release.
5. **The file changed after the scan**, from the editor or a dirty git tree. Check the file hash before writing; if it changed, re-scan instead of splicing.

### 6. What this suggests for the plan
1. **Engines:** tree-sitter WASM for Python and the TypeScript compiler API for TS/JS. Run both in a worker or `utilityProcess` with no native modules.
2. **Prompt model:** an ordered list of pieces, each one an editable literal, a code placeholder, a template variable, or a runtime value. Every editable piece records where it came from.
3. **Mapping file:** give each step a stable ID made of file + enclosing function + rule + slot path, with a content-hash fallback, so the file survives line changes. Add a `verify` command for CI.
4. **First scope:** direct SDKs (Anthropic, OpenAI, Gemini), raw HTTP, Vercel AI SDK and LangChain/LangGraph. Add CrewAI YAML, LlamaIndex, Mastra and DSPy later.
5. **CLI/MCP first:** ship the CLI/MCP server early, since Codag shows coding agents want this. Export test cases to Promptfoo rather than building our own eval suite.

### Insights and gaps from the registries scan

- The market is consolidating into larger data, security and model companies. Humanloop's team went to Anthropic (product shut 8 Sep 2025), ClickHouse bought Langfuse (Jan 2026), Mintlify bought Helicone (Mar 2026, now in maintenance), OpenAI bought Promptfoo (Mar 2026), and Palo Alto bought Portkey (Jun 2026). Standalone prompt registries are being folded into observability, security and agent platforms.
- Almost every platform uses a 'registry as source of truth' model: prompts are moved out of code and fetched at runtime by name and label. The only code-first options are eval tools (Braintrust push, Promptfoo YAML) or framework-specific ones (Mirascope/Lilypad, Vellum Workflows SDK, LangGraph Studio). None of them read arbitrary existing SDK calls back out of a codebase.
- Visual workflow views come in two kinds. Builder canvases (Vellum, PromptLayer Agent Builder) make you build the workflow inside their product. Runtime trace graphs (Langfuse, Phoenix, LangSmith) only show what already ran. LangGraph Studio draws from code, but only for LangGraph and without editing prompts.
- Vendors are moving from prompt management toward agent observability and evals: Latitude's June 2026 relaunch, LangSmith Fleet and Engine, and failure clustering. Prompt editing is becoming a small feature inside larger eval and trace suites, which leaves room for a focused developer tool.
- Gap: Discovering prompts from existing code: no product scans a Python or TS repo and finds every LLM call site (raw SDKs, LangChain, LlamaIndex, CrewAI, Vercel AI SDK, HTTP) without changes to the code. Static analysis like AgentFlow exists only as research. Recaller Code could be the first product to do this.
- Gap: Editing a prompt where it sits in the code, then opening a commit or PR: every competitor either moves prompts into a registry with a runtime dependency, or into separate YAML or PromptL files. A tool that edits the string literal in place (with {placeholders} and multi-piece prompts) and ships through the normal deploy has no runtime fetch, no vendor lock-in and no extra point of failure. That matters more now that several registries have been acquired or put into maintenance.
- Gap: A board or flow of the product's actual workflows, built from the code across frameworks: existing views are either canvases you build inside the tool or graphs of runtime traces, and Studio works only for LangGraph. A per-workflow kanban with an AI-proposed, user-confirmed mapping saved in a repo file is new.
- Gap: Local and agent-first: none of the leaders ships a desktop app or an MCP server for editing prompts in code. A CLI/MCP that lets Claude Code or Cursor list, test and edit workflow prompts fits how developers now work, and it can export test cases to Promptfoo or Braintrust instead of competing with them on evals.

### Insights and gaps from the code-first scan

- Discovery of LLM calls in code now exists, but split into two halves that don't meet. Security tools (Snyk AI-BOM, Trusera ai-bom, AIROM, SafeDep, xgrep, ZeroPath) produce CycloneDX AI-BOMs for compliance. Dev tools (Codag) draw a graph of the calls. None of them lets you edit or test the prompt where it sits.
- Prompts as files in git is the mainstream code-first answer: BAML .baml, Dotprompt .prompt, Prompty .prompty, GitHub Models .prompt.yml, POML. All of them make you move the prompt out of your existing code into their format. Leaving prompts in place as string literals is not offered by any major player.
- The opposite camp is growing: runtime-fetched managed prompts with rollouts (Pydantic Logfire managed variables, Lilypad). Even Pydantic concedes that source-controlled prompts suit teams with infrequent changes, which validates the no-runtime-fetch stance for many teams.
- Consolidation is underway: OpenAI announced the Promptfoo acquisition on Mar 9, 2026, and Microsoft folded the AI Toolkit into Foundry. Evals and red-teaming are being absorbed by model vendors, so a neutral, multi-provider, local-first tool has room.
- Gap: Combining find + view + edit-in-place + test: Codag shows the graph but can't edit, blogus finds prompts but rewrites them into load_prompt(), BAML and Prompty make you migrate. An editor that writes back to the original string literals (with {placeholders} and multi-piece prompts) appears to be unoccupied.
- Gap: Workflow grouping a person has confirmed and saved in a repo file: existing graphs are either derived from the call graph or labeled by an LLM each time. A committed mapping file (workflow to ordered steps) that CI and agents can read is new, and could double as a lightweight AI-BOM.
- Gap: PR-native prompt changes for inline prompts: GitHub Models and the Promptfoo Action gate PRs only for prompts in their own file formats. Generating a commit or PR for an inline-string edit, with a before/after eval attached, is open.
- Gap: Non-engineer access: every tool found lives in VS Code or a CLI. A standalone desktop board for PMs and domain experts that still produces a git PR could reach users these tools don't serve.

### Insights and gaps from the visual scan

- Split model: every visual builder (Langflow, Flowise, Dify, n8n, AutoGen Studio) only edits workflows that run on its own runtime. None reads plain application code. The code-and-UI-in-sync attempts are Vellum push/pull, Rivet project files and Prompt flow YAML. Each needed its own file format or SDK, and Vellum and Prompt flow have both retreated: Vellum pivoted to a consumer assistant, and Prompt flow retires in April 2027. LangGraph Studio is the closest to 'read your code', but only for LangGraph and only read/run, not editing the source.
- Consolidation in 2025-26: Flowise went to Workday, DataStax/Langflow to IBM, Langfuse to ClickHouse, Traceloop to ServiceNow, and AutoGen is in maintenance mode, replaced by Microsoft Agent Framework. Standalone visual LLM-builder startups are being absorbed into platforms, which leaves room for a developer-side, code-native tool.
- Visual metaphors: node-and-wire canvases are the default for building flows but get messy for real app code (branches, loops, helper functions). Observability tools have moved toward trace trees and timelines, transcripts (Laminar), and inferred graphs with an aggregated mode (same-name steps merged, with counts) and an expanded mode (loops unrolled into a DAG) (Langfuse, July 2026). For mostly linear LLM pipelines, an ordered column or swimlane per workflow (Recaller's kanban) reads better than a free canvas. Keep a DAG view for branches.
- Tracing already finds the multi-step structure of real code automatically (OpenLLMetry auto-instrumentation, Langfuse graphs inferred from spans). That is a complementary way to find workflows: optionally import traces to confirm or correct Claude's static call-to-workflow mapping.
- Gap: No tool statically finds the LLM calls in existing Python/TS code across raw SDKs and frameworks and edits the prompt string literals in place. Builders need their runtime, tracers are read-only, and LangGraph Studio is limited to one framework.
- Gap: Prompt changes as git commits/PRs: only n8n (Business plan, workflow JSON) and the file-based tools (Rivet, Prompt flow) touch git. None opens a PR for a prompt edit in application source. That fits teams that won't fetch prompts at runtime from a registry.
- Gap: A cross-framework 'workflow map' saved in the repo (the confirmed call-to-workflow mapping file), which could also be checked against production traces (OTel/OpenLLMetry) to flag drift or unmapped LLM calls.
- Gap: Per-step testing in context: test one step with inputs generated from the previous step's output, or from real trace payloads. Builders do this only inside their own runtime, and tracers don't link it back to the line of code.

## Appendix: the Python scanner

**Recommended approach:** Use web-tree-sitter (WASM) with the tree-sitter-python grammar as the single parsing engine inside Electron's Node side (worker thread). The same engine with tree-sitter-typescript covers the TS/JS half, and it needs no Python on the user's machine and no native rebuilds. Pipeline: (1) Parse every .py file and build a per-repo index: imports and aliases, module/class-level string constants, and receiver types from constructor assignments. (2) Match LLM call sites against a data-driven catalog (JSON) of FQN methods plus argument roles: messages.create -> system/messages[].content, responses.create -> instructions/input, generate_content -> contents/system_instruction, ChatPromptTemplate.from_messages, PromptTemplate.from_template, create_agent system_prompt / create_react_agent prompt, Agent role/goal/backstory, Task description/expected_output, pydantic_ai Agent instructions/system_prompt, DSPy Signature docstring/desc, raw httpx/requests URLs. Seed the catalog from the OpenLLMetry and Cisco aibom lists. Also scan YAML (CrewAI), .j2/.txt prompt files referenced by literal paths, and one level of user wrapper functions. (3) Trace each prompt argument back to literal pieces. Produce a Prompt model: an ordered list of pieces, each either an editable literal span (file, byte range, prefix, quote, raw/f/dedent flags, template dialect) or a placeholder (source text, display name). Attach a confidence and a provenance chain. (4) Rewrite by Buffer splicing of string_content spans only, applying the escape rules for the literal's dialect. Then re-parse to confirm no ERROR nodes, re-evaluate the literal to confirm the round trip, check the file hash, and hand off to the git commit/PR flow. (5) Send low-confidence or unresolved calls to Claude: ask which workflow they belong to, and save the confirmed mapping in the repo file. Keep an optional precision mode: if Python 3.12+ is detected on the machine, run a small LibCST/ast sidecar for QualifiedNameProvider resolution and for a final `compile()` check of edited files. Never make it required. Pyodide is a fallback for the ast validation if wanted later.

**Where prompts sit in calls** (seed for the call catalog):

- **anthropic**: client.messages.create(model=..., system=str \| list[{type:'text', text:...}], messages=[{role, content: str \| list[{type:'text', text}]}]). Also AsyncAnthropic, .messages.stream(...), .beta.messages.create, AnthropicBedrock/AnthropicVertex clients. Prompt = system kwarg + every content text in messages. Example: `client.messages.create(model="claude-...", system="You classify support tickets.", messages=[{"role": "user", "content": f"Ticket:\n{ticket.body}"}])`

Example: `client.responses.create(model="gpt-...", instructions="Extract fields as JSON.", input=f"Ticket: {text}")`

**String forms to handle:**

- Plain literals, any quote style ('', "", ''', """), with prefixes r/R, b, u, f/F, rf/fr, and Python 3.14 t-strings (PEP 750) -> editable directly.
- f-strings: literal parts editable, {expr!r:fmt} interpolations shown as {placeholder}; Python 3.12+ (PEP 701) allows nested same-type quotes and multiline expressions inside {} - parser must support this.
- Implicit concatenation ("a" "b" across lines in parens) -> one prompt, several pieces, each piece edited in its own literal.
- + concatenation and += building, ''.join([...]), '\n'.join(parts) -> pieces; non-literal operands become placeholders.
- str.format: "...{name}...".format(name=x) -> literal braces are already placeholders; {{ }} are escaped braces.
- %-formatting: "...%s..." % x and %(name)s -> render as {placeholder}; %% is a literal percent.
- Template-engine braces in framework strings: LangChain/LlamaIndex/CrewAI {var} are filled later by the framework, not by Python; distinguish from Python f-string {expr}.
- textwrap.dedent("""...""") and inspect.cleandoc -> display dedented, but edit the raw literal and re-indent lines to the original common indent.
- Constants: module-level PROMPT = "..." or class attributes, imported from prompts.py (from .prompts import SYSTEM) -> follow import to the defining literal.
- Jinja2 templates: Template("...{{ x }}...") or env.get_template('x.j2') -> {{ }} / {% %} syntax; edit the .j2 file, show variables as placeholders.
- Prompts in files read at runtime: open('prompts/x.txt').read(), Path(...).read_text(), yaml.safe_load (CrewAI), json, importlib.resources -> edit the file (still in repo, still ships with deploy) when the path is a resolvable literal.
- Dynamic/opaque: hub.pull, DB/env lookups, prompts built in loops or functions with many branches -> mark as read-only/'not statically resolvable'.

**Parser options:**

- **web-tree-sitter + tree-sitter-python WASM**: string node = string_start, (string_content \| interpolation)*, string_end; interpolation has fields expression/type_conversion/format_specifier; concatenated_string groups implicit concatenation; escape_sequence nodes exposed. Gives syntax only - no name resolution or types; we build import/assign resolution ourselves. Same toolchain covers TypeScript/JS (tree-sitter-typescript), so one engine for both halves. Check grammar version for PEP 701 nested-quote f-strings and 3.14 t-strings. Offsets are bytes of UTF-8 - convert carefully to JS string indices. Lossless rewrite: Yes for our purpose: every node has exact startIndex/endIndex byte offsets, so we splice text into the original buffer and never re-print. Error-tolerant (parses broken files).. In Electron without Python: Yes. Pure WASM in Node/Electron main or renderer; prebuilt python .wasm ships on tree-sitter-python GitHub releases and in tree-sitter-wasms npm. Native node 'tree-sitter' bindings are faster but need electron-rebuild..
- **LibCST**: Used by Cisco aibom for exactly this problem (resolving fully qualified symbols to find AI components). Best choice if a Python sidecar is acceptable. Lossless rewrite: Yes, best-in-class: full CST round-trips byte-for-byte, FormattedString/ConcatenatedString/SimpleString nodes, codemod framework, ScopeProvider and QualifiedNameProvider metadata for name resolution.. In Electron without Python: No. Needs CPython plus a Rust native extension (the default parser). Could bundle a frozen Python sidecar (PyInstaller) per OS, or possibly Pyodide (unverified whether libcst's native wheel exists for Pyodide)..
- **Python ast (end_lineno/end_col_offset)**: Good as a validator: after splicing, re-parse with ast to confirm the file still compiles and that the literal's evaluated value equals the intended new text. Lossless rewrite: Not by unparse (ast.unparse drops comments/formatting), but yes by splicing using node positions. col_offsets are UTF-8 byte offsets. Positions of Constant parts inside JoinedStr (f-string) only reliable on 3.12+.. In Electron without Python: No natively; yes via Pyodide (CPython compiled to WASM, ~10 MB+, runs in Node). Gives exact parse for the Python version Pyodide bundles..
- **parso**: Pure Python so Pyodide-friendly; weaker maintenance and f-string detail than LibCST; no scope/qualified-name metadata like LibCST. Lossless rewrite: Yes, round-trips and error-tolerant (powers Jedi).. In Electron without Python: No (pure Python; would run under Pyodide)..
- **Others**: ast-grep is attractive as a rule layer on top of tree-sitter (patterns like `$C.messages.create($$$ARGS)`) but adds a native module to Electron. Lossless rewrite: ast-grep supports rewrite by byte span; Ruff has exact ranges.. In Electron without Python: Ruff/ruff_python_parser (Rust) could be compiled to WASM but no official npm package for its AST; ast-grep (@ast-grep/napi, tree-sitter based, native addon) gives pattern-matching rules in YAML; Semgrep needs its own binary/OCaml engine..

**Following a variable back to its string:** Build a lightweight, per-repo symbol index on top of the tree-sitter parse (no type checker needed for 90% of cases): 1. Import map per module: `import openai`, `from anthropic import Anthropic as A`, `from .prompts import SYSTEM`, relative imports resolved against package dirs (__init__.py, src/ layout, pyproject packages). Store alias -> fully qualified name. 2. Receiver resolution for calls: `client = Anthropic()` / `self.client = OpenAI()` / `llm = ChatOpenAI(...)` -> record the variable/attribute's class FQN, so `client.messages.create` and `self.client.responses.create` resolve to the SDK method. Also accept a heuristic match on the method chain (`.messages.create`, `.chat.completions.create`, `.responses.create`, `.models.generate_content`) with lower confidence. 3. Value tracing for prompt arguments: from the argument expression, walk back within the function to the nearest assignment (single static assignment preferred), then enclosing scopes (class attrs via self.X, module globals), then follow `from m import X` into module m's top-level assignment. Recurse through +, implicit concat, f-strings, .format, %, dedent, join, dict/list literals (messages=[...]) and simple helper functions that `return` a string (inline one level, treating parameters as placeholders). 4. Stop rules: multiple reaching assignments, loop-built strings, function params from callers -> become {placeholder} named after the variable; mark confidence. 5. Store a provenance chain (call site -> var -> file:range of literal) so edits go to the defining literal, and reverse index literal -> call sites to warn on shared prompts. 6. Optional precision layer later: run Pyright/Jedi or LibCST QualifiedNameProvider in a sidecar when Python exists; and Claude can resolve the leftover low-confidence cases (it already proposes workflow mapping).

**Safe rewrite rules:**

- Never re-print the file. Splice only the byte range of each string literal (or of the string_content parts inside it); everything else stays byte-identical. Verify by diffing: only the targeted ranges changed.
- Keep the original prefix (r, f, rf, b, u, t) and quote style (' " ''' """). Only switch to triple quotes if the user adds a newline to a single-line literal and escaping \n is not acceptable - default to escaping as \n to keep the literal's shape.
- Escape for the target literal: in non-raw strings escape backslash first, then the active quote char, then control chars (\n, \t, \r) unless triple-quoted where real newlines are allowed; inside triple quotes escape a run of three quote chars and a trailing quote at the end.
- Raw strings: cannot contain the closing quote unescaped nor end with an odd number of backslashes; if the new text can't be represented, refuse or convert to a non-raw literal with explicit user confirmation.
- f-strings: edit only string_content nodes, never interpolation nodes; any literal { or } typed by the user becomes {{ / }}. Placeholders shown in the UI as {name} are bound to their original interpolation source text and re-emitted verbatim; user cannot create new interpolations (or can only re-use existing ones).
- str.format / LangChain / LlamaIndex / CrewAI templates: placeholders are part of the literal text; a literal brace typed by the user must become {{ }}; warn when the set of {vars} changes (adding a var the caller doesn't supply = KeyError at runtime). For Jinja keep {{ }}/{% %} untouched.
- %-format strings: literal % must become %%; keep the count/order of %s specifiers.
- Implicit concatenation: map edits back to each piece separately; keep piece boundaries and line breaks; if the user edits across a boundary, put the change in the earlier piece. Preserve the per-piece prefix (pieces can mix f and non-f).
- textwrap.dedent / cleandoc: show dedented text; on write, re-add the original common leading whitespace to every non-empty line, keep the leading backslash-newline or first-line convention and trailing newline exactly as before.
- Preserve file encoding, BOM and line endings (CRLF vs LF) - detect from file and use it for new newlines in triple-quoted strings.
- After each rewrite: re-parse (tree-sitter and, if available, Python ast) and evaluate the literal parts to confirm the evaluated string equals the user's intended text with placeholders intact; abort the write on mismatch.
- Refuse to edit when the source changed since scan (compare file hash), when the literal is shared by several call sites (warn: 'used by N prompts'), or when it's a bytes literal.

**Risks:**

- tree-sitter-python version lag: PEP 701 (3.12) nested-quote/multiline f-strings and PEP 750 t-strings (3.14) may parse with errors in older grammar builds - pin and test a recent grammar; fall back to read-only when ERROR nodes overlap a prompt.
- Byte vs UTF-16 offsets: tree-sitter and Python ast report UTF-8 byte offsets; JS strings are UTF-16. Splice on a Buffer, not on a JS string, or non-ASCII prompts (emoji, accents) get corrupted.
- Framework template braces vs Python braces: confusing an f-string {expr} with a LangChain {var} produces wrong escaping and runtime KeyError/format errors.
- Prompts shared across call sites or across workflows: editing one constant changes several steps - must surface this.
- Dynamic prompts (hub.pull, DB, env, loops, callables like @agent.instructions or @dynamic_prompt) can't be fully shown or edited statically.
- API churn: create_react_agent(prompt=) -> create_agent(system_prompt=); OpenAI chat.completions vs responses; google.generativeai -> google-genai; Pydantic AI system_prompt vs instructions. Keep the catalog data-driven and updatable (borrow from OpenLLMetry/aibom lists).
- Wrapper functions in user code (def ask_llm(prompt): return client.messages.create(...)) hide the real call sites; need one-level interprocedural inlining, otherwise every workflow step collapses to the wrapper.
- Pyodide/LibCST sidecar adds 10-50 MB and per-OS packaging complexity; native node tree-sitter needs electron-rebuild per Electron version.
- Rewrites racing with the user's editor: verify file hash before write; integrate with git (dirty working tree) cleanly.
- Unverified points from this fast pass: whether LibCST works under Pyodide; exact current tree-sitter-python PEP 701 coverage; exact Semgrep rule contents.

## Appendix: the TypeScript/JavaScript scanner

**Recommended approach:** Use the TypeScript compiler API (typescript 5.x/6.x, pinned) as the TS/JS scanner core, with ts-morph optional for navigation convenience. Apply all edits as span splices with magic-string, never with a printer. Why: it is pure JS (no native modules to package or to get flagged by AV in Electron), it parses TS/TSX/JS/JSX exactly as the user's build does, it gives UTF-16 spans matching JS strings, and its TypeChecker/LanguageService solves the hardest part (following imported constants, barrels, path aliases and object properties back to the literal) for free. Pipeline: (1) In an Electron utilityProcess, find tsconfig/jsconfig projects and build one ts.Program per project (allowJs, no diagnostics). (2) Pass 1, cheap prefilter: grep files for imports of known packages (@anthropic-ai/sdk, openai, @google/genai, @google/generative-ai, ai, @ai-sdk/*, @langchain/*, langchain, llamaindex, @llamaindex/*, @mastra/core, @openai/agents) or LLM API URLs, so only those files and their dependencies are walked. (3) Pass 2: a data-driven rule table (JSON/YAML, versioned per library) maps call shapes to prompt slots, e.g. {module:'@anthropic-ai/sdk', path:'*.messages.create\|stream', slots:['arg0.system','arg0.messages[*].content']}, {module:'ai', fn:'generateText\|streamText\|generateObject\|streamObject', slots:['system','prompt','messages[*].content']}, {module:'@mastra/core/agent', ctor:'Agent', slots:['instructions']}. Confirm receivers via the checker (the type's declaration comes from that package), so aliased clients and wrappers typed with SDK types still match. (4) For each slot expression, a resolver turns it into a PromptModel of pieces: literal (with file, span, raw, cooked, quote kind, tag), placeholder (expression source), or external (runtime). It follows identifiers with checker.getSymbolAtLocation + getAliasedSymbol, recurses through template/concat/join/builder functions/object properties, and handles ?raw and readFileSync text files as whole-file pieces. (5) Wrapper detection: if a slot resolves to a parameter of a local function, record that function as a wrapper and treat its call sites as LLM calls (iterate to a fixpoint), and let Claude propose or confirm ambiguous ones. This plugs directly into the user-confirmed workflow mapping file. (6) Writes: per-piece span edits with the escaping rules above, a hash check before writing, re-parse verification after, then a git diff, commit or PR. Keep a stable ID per prompt slot (file + enclosing function name + rule + slot path, with a content hash fallback) so the workflow-mapping file survives line shifts. For the Python half and a single shared query layer, consider web-tree-sitter (WASM, Python + TS grammars) as a fast error-tolerant first pass. ast-grep's rule syntax is a nice way to author the rule table if you accept a native module. But for TS/JS, the TypeScript checker's cross-module resolution is worth the ~25MB dependency. Do not embed Semgrep or CodeQL. Mine CodeQL's 2.26 prompt-injection sink models and observability instrumentation lists as a checklist when writing the rule table.

**Where prompts sit in calls** (seed for the call catalog):

- **@anthropic-ai/sdk**: client.messages.create({ model, system, messages:[{role, content}] }). system can be a string or an array of {type:'text', text} blocks (often with cache_control). content can be a string or an array of content blocks ({type:'text', text}). messages.stream() takes the same shape. The legacy completions.create({prompt}) also exists. Anchor detection on the import of '@anthropic-ai/sdk' plus the call path .messages.create/.stream, including on aliased client variables. Example: `await anthropic.messages.create({ model: 'claude-x', max_tokens: 1024, system: 'You classify tickets for ${company}.', messages: [{ role: 'user', content: ticket.body }] })`
- **openai (Node)**: chat.completions.create({ messages:[{role:'system'\|'developer'\|'user', content}] }), where content is a string or an array of {type:'text', text} parts. responses.create({ instructions, input }), where input is a string or an array of {role, content}. The beta parse() variants have the same shape. The AzureOpenAI client and OpenAI-compatible baseURL clients (Groq, Together, OpenRouter) use the same calls. Example: `await openai.responses.create({ model: 'gpt-x', instructions: 'Extract fields as JSON.', input: 'Ticket:\n${text}' })`
- **@google/genai**: ai.models.generateContent / generateContentStream({ model, contents, config:{ systemInstruction } }). contents can be a string, a Part, or Content[] with parts:[{text}]. systemInstruction can be a string, string[] or Content. ai.chats.create({config:{systemInstruction}}) then chat.sendMessage({message}). Example: `await ai.models.generateContent({ model: 'gemini-x', contents: 'Write a reply to: ${ticket}', config: { systemInstruction: ['You are a support agent.', 'Be brief.'] } })`
- **Vercel AI SDK (ai)**: generateText / streamText / generateObject / streamObject({ model, system, prompt, messages }). prompt is a string (or messages in newer versions). messages is ModelMessage[] with content as a string or parts [{type:'text', text}]. generateObject also takes schema plus schemaDescription. - **LangChain.js / LangGraph.js**: ChatPromptTemplate.fromMessages([['system', '...{var}...'], ['human', '{input}']]), PromptTemplate.fromTemplate('...{x}...'), new SystemMessage('...'), new HumanMessage(...), model.invoke('string' \| messages), createReactAgent({ llm, tools, prompt\|stateModifier }) and createAgent({ systemPrompt }). The runtime variables here are LangChain's own {var} (f-string) or {{var}} (mustache) syntax inside a plain literal, so the text must be shown as-is and the braces must not be re-escaped. Prompts can also be pulled from the LangChain Hub (hub.pull) at runtime. Flag these as non-editable. Example: `const prompt = ChatPromptTemplate.fromMessages([['system', 'Classify the ticket into {categories}.'], ['human', '{ticket}']]); await prompt.pipe(model).invoke({ categories, ticket })`
- **LlamaIndex.TS**: llm.complete({ prompt }), llm.chat({ messages:[{role, content}] }), the older new OpenAIAgent({ llm, tools, systemPrompt }), the newer agent({ llm, tools, systemPrompt }) from @llamaindex/workflow, and PromptTemplate({ template: '...{query}...' }) passed to query engines through updatePrompts. The LLM comes from openai()/anthropic() factories in @llamaindex/*. The API has churned across versions, so match several shapes. Example: `const llm = openai({ model: 'gpt-x' }); await llm.complete({ prompt: 'Summarise: ${doc}' })`
- **Mastra (@mastra/core)**: new Agent({ id, name, instructions, model, tools }). instructions can be a string, a string[] or a function. Then agent.generate(input) / agent.stream(input), where input is a string or messages. Tool descriptions (createTool({ description })) and workflow steps (createStep) can also contain prompt-like text. Workflow steps give a natural column order. Example: `export const triageAgent = new Agent({ name: 'triage', instructions: 'You route support tickets to the right team.', model: openai('gpt-x') }); await triageAgent.generate('Ticket: ${t}')`
- **OpenAI Agents SDK JS (@openai/agents)**: new Agent({ name, instructions, tools, handoffs, outputType }) or Agent.create(...), then run(agent, input). instructions can be a string or a function (ctx, agent) => string, so a dynamic function body should be treated as a 'built prompt'. handoffDescription and tool({ description }) also feed the model. Example: `const writer = new Agent({ name: 'Writer', instructions: 'Write a friendly reply.' }); const r = await run(writer, 'Ticket: ${body}')`
- **raw fetch / axios / ky**: fetch('https://api.anthropic.com/v1/messages' \| 'https://api.openai.com/v1/chat/completions' \| '/v1/responses' \| 'https://generativelanguage.googleapis.com/v1beta/models/...:generateContent', { body: JSON.stringify({ system, messages \| input \| contents }) }). Detect by URL literal or constant, then follow the JSON.stringify argument object. Same JSON keys as the SDKs, but in Gemini REST the system field is spelled system_instruction/systemInstruction. Bodies built in a separate variable need one hop of dataflow. Example: `await fetch('https://api.anthropic.com/v1/messages', { method: 'POST', headers, body: JSON.stringify({ model, max_tokens: 512, system: SYSTEM_PROMPT, messages: [{ role: 'user', content: q }] }) })`

**String forms to handle:**

- Plain string literals in ' or ": the editable span is the content between the quotes. Escape sequences (\n, \', \u{...}) must be decoded for display and re-encoded on write.
- Template literals without expressions (`...`): multi-line, so this is the most common form for long prompts.
- Template literals with ${expr}: split into quasis (static pieces) and expressions. Show each expression as {placeholder}, named from its source text (${user.name} -> {user.name}, a complex expression -> {expr1}). Only the quasis are editable. The user must not delete or reorder placeholders unless the editor explicitly supports that, which rewrites the expression source text verbatim.
- Tagged templates such as dedent`...`, outdent`...`, ts-dedent, common-tags stripIndent/oneLine, and LangChain's own tags. The tag changes runtime text: dedent strips the common indentation and the first/last newline. Show the cooked text after applying the tag's semantics for display, but write back in raw form with the original indentation re-applied. String.raw`...` means backslashes are literal, so do not escape them.
- + concatenation ('a' + b + `c`) and += accumulation in a let variable: show as pieces, with literal pieces editable and non-literals as {placeholders}. += across branches (if/else) makes the prompt conditional, so show it as a 'built prompt', read-only or editable only per piece.
- Arrays joined: ['line 1', `line ${x}`, ...].join('\n') or join(''). Each element is a piece, and the separator is part of the semantics. Also covers string[] accepted directly by Gemini systemInstruction and Mastra instructions.
- Builder functions (const buildPrompt = (t) => `...${t}...`), including arrow functions that return a template. Follow the callee to its return statement and present it as a template whose parameters are the placeholders.
- Constants and exports from other modules (export const SYSTEM_PROMPT = `...`; import { SYSTEM_PROMPT } from './prompts'), including re-exports (export * from), barrel files, path aliases from tsconfig paths, `as const` and `satisfies` wrappers, and object properties (PROMPTS.classify, PROMPTS['classify']).
- Text files imported as strings: Vite `import p from './p.md?raw'`, webpack asset/source or raw-loader, Bun/esbuild `with { type: 'text' }` / loader text, Next.js turbopack raw rules, and fs.readFileSync(path.join(__dirname, 'prompt.txt'), 'utf8') at runtime. These are great targets because the whole file is the prompt, so edit the file, not a literal (no escaping needed).
- JSON or YAML files (import prompts from './prompts.json', with { type: 'json' }) and property access into them. Rewrite the JSON value using JSON string escaping and keep the file's formatting with a span-based edit (jsonc-parser's modify/applyEdits is lossless).
- Prompt-template DSLs inside literals: LangChain {var} / {{var}} mustache, LlamaIndex {query}, Handlebars or Mustache, and Jinja-like nunjucks. These are already placeholders, so show them as placeholders without changing the text, and do not treat their braces as code.
- Message arrays and content blocks: {role:'system', content: X} and {type:'text', text: X}. X can be any of the forms above, and each message is one 'piece' of a step's prompt.
- Values that cannot be resolved statically: env vars, DB or remote fetches (hub.pull, Langfuse/PromptLayer getPrompt), function parameters with many callers. Show them as an opaque {placeholder} with a 'defined at runtime' marker and never make them editable.

**Parser options:**

- **TypeScript compiler API (typescript package)**: The reference parser for TS/TSX/JS/JSX. Nodes carry exact positions (getStart(sf) and getEnd(), UTF-16 offsets matching JS strings), and the parsed text of a literal (rawText for template parts) is available. You never need its printer: read spans from the AST and splice new text into the original source string, so the rewrite is lossless. It includes the TypeChecker and LanguageService for cross-module symbol resolution (see tracing). It is a single pure-JS dependency (~20-25MB), which matters for the Electron bundle size. Note that TypeScript 7 (Go port, tsgo) is becoming the main compiler, but the JS API from TypeScript 5.x/6.x stays available on npm, so pin 5.x/6.x for the API. Lossless rewrite: Yes, if you splice by span (or use magic-string). Do not use ts.createPrinter on the whole file, because it reformats.. In Electron without Python: Yes. Pure JS, runs in the Electron main process or a utilityProcess/worker..
- **ts-morph**: A wrapper around the TypeScript compiler API with an ergonomic navigation API (getDefinitionNodes, findReferences, getLiteralText, setLiteralValue, replaceWithText). The manipulation API re-parses after every edit and is slow on large files (per the docs' performance page). Use it for analysis and navigation, then apply edits yourself by span. Projects can be created from tsconfig, with skipFileDependencyResolution and in-memory file systems available. Lossless rewrite: replaceWithText on a single literal node preserves the rest of the file. Batching many edits via spans is faster and equally lossless.. In Electron without Python: Yes (pure JS, bundles typescript)..
- **web-tree-sitter + tree-sitter-typescript/tsx (WASM)**: Fast, error-tolerant, incremental, concrete syntax tree. Works on broken or partial code, and one runtime covers Python and TS/JS, which fits Recaller's two-language scanner. Grammars come as .wasm (tree-sitter-typescript ships typescript and tsx grammars, and tree-sitter-javascript covers JS). The query language (S-expression patterns) is handy for call-site matching. There is no type or symbol resolution, so cross-module tracing must be built yourself (an import graph plus scope lookups). For Electron, the web-tree-sitter README says to use the CommonJS build (web-tree-sitter.cjs). Native node bindings need electron-rebuild, which WASM avoids. CAUTION: positions are byte offsets in the UTF-8 encoding of the source (startIndex), not UTF-16 string indexes, so convert before splicing any file with non-ASCII text (emoji, curly quotes and accents are common in prompts). Lossless rewrite: Yes, by span splice (after converting byte to UTF-16 offsets or working on a Buffer).. In Electron without Python: Yes (WASM)..
- **oxc-parser (napi) + magic-string**: The fastest JS/TS parser (Rust, N-API prebuilt binaries per platform). Returns an ESTree / TS-ESTree AST with start/end spans, plus a ready-made ESM import/export table (staticImports/staticExports), which helps build the module graph cheaply. The oxc docs explicitly suggest pairing it with magic-string for rewrites. Newer versions convert spans to UTF-16 for the JS side. Check the version you pin. No type checker. oxc's resolver (oxc-resolver) handles tsconfig paths and package exports. Native binary: per-platform packages must be included in the Electron build (asarUnpack). Lossless rewrite: Yes via magic-string span edits.. In Electron without Python: Yes (N-API prebuilds for win/mac/linux x64/arm64, no rebuild needed for Node-API, but they must be packaged). A wasm32-wasi build also exists..
- **Babel parser + recast**: recast.parse with @babel/parser (typescript, jsx plugins) preserves original formatting for untouched nodes and reprints only modified ones. The classic codemod stack (also jscodeshift). Slower, with occasional quirks reprinting edited parents (parentheses, comments) and template literal reprinting. Since we only replace literal contents, span splicing via @babel/parser node.start/end is simpler and safer than recast printing. Lossless rewrite: Mostly (recast). Fully if you splice by span.. In Electron without Python: Yes (pure JS)..
- **SWC (@swc/core)**: Fast Rust parser, but its JS-side AST spans are global byte positions offset across parse calls (a long-standing gotcha), and its printer is not formatting-preserving. Fine for parsing, awkward for precise rewrites. Not recommended here. Lossless rewrite: Only via manual span splicing after correcting the span offset quirk.. In Electron without Python: Yes (native binary)..
- **ast-grep (@ast-grep/napi)**: tree-sitter-based structural search/replace with pattern syntax ($A, $$$ARGS) and YAML rules. Very convenient for writing detector rules for each SDK call shape, and also supports Python. Native binary. Rewrites are text-span based (lossless). Lossless rewrite: Yes.. In Electron without Python: Yes (N-API prebuilds)..
- **Semgrep / CodeQL**: Strong dataflow engines, but they are external CLIs (Semgrep OSS is Python/OCaml; CodeQL needs a database build and has a restrictive license for commercial closed-source use). Not suitable to embed in a sold desktop app. Use them only as inspiration for sink lists. Lossless rewrite: N/A. In Electron without Python: No (separate binaries; CodeQL licensing is restrictive)..

**Following a variable back to its string:** Use a ts.LanguageService (or ts.Program + TypeChecker) built from the repo's tsconfig(s). For JS-only repos, use allowJs/checkJs-free defaults or a synthesized config with allowJs:true, moduleResolution bundler, and paths from jsconfig.json. Steps: (1) at a call-site argument node, call checker.getSymbolAtLocation(node). If it is an alias (import), call checker.getAliasedSymbol(symbol) to jump through imports, re-exports and barrels. (2) Take symbol.valueDeclaration. For a VariableDeclaration, read the initializer and unwrap `as const`, satisfies, parentheses, type assertions and non-null. For a PropertyAssignment/ShorthandPropertyAssignment in an object literal (PROMPTS.classify), resolve the property symbol via the checker. For a function or arrow, inspect return statements. (3) Recurse into the initializer's form (template, concat, join, call) with a cycle guard and depth limit (around 8). (4) Equivalently, use languageService.getDefinitionAtPosition(file, pos) or ts-morph's identifier.getDefinitionNodes(), which wraps the same thing. (5) For `const` with literal types, checker.getTypeAtLocation(node) gives a string literal type with the exact value. Useful as a quick check, but you still need the declaration node to edit it. (6) For ?raw / text imports, the TS checker sees them as `declare module '*?raw'` from an ambient d.ts, so resolve the module specifier yourself (strip the query, resolve relative to the file, and use bundler config for aliases) and treat the file as the editable prompt. (7) Keep a per-file reverse index (declaration -> all call sites) via languageService.findReferences, so the UI can warn 'this constant is used by 3 LLM calls; editing changes all of them'. Performance: create the Program once per scan, reuse it, and update incrementally with a LanguageServiceHost whose getScriptVersion bumps on file changes (watch mode). Skip type-checking diagnostics; symbol resolution is enough. Monorepos: one Program per tsconfig project (follow references) or a solution-style root. Fallback when there is no tsconfig or the TS service fails: a lightweight import graph from oxc-parser's staticImports plus oxc-resolver, with name-only lookups of exported const declarations. This covers about 90% of prompt constants without the type checker.

**Safe rewrite rules:**

- Never reprint the AST. Compute edits as (start, end, newText) over the original file text, apply them in descending start order (or via magic-string), and touch only the inside of the literal (between the delimiters), so delimiters, comments, formatting, line endings and the rest of the file are byte-identical.
- Before writing, re-read the file and compare a hash (or the exact old literal text at that span) with what was scanned. If it differs, re-scan rather than splice, which protects against the user or IDE editing the file concurrently.
- Template literal quasis: escape \ as \\ first, then ` as \`, then ${ as \${ (only the sequence '${' needs escaping; a lone $ or { is fine). Do not escape newlines; keep real newlines. Preserve CR/LF style: if the file uses CRLF, emit CRLF inside the literal too, but note that template literals normalize CRLF to LF at runtime, so the prompt text is the same either way.
- Placeholders: each ${expr} keeps its original expression source text verbatim. The editor works on [quasi, placeholder, quasi, ...] and you rebuild the literal as quasi0 + '${' + exprSrc0 + '}' + quasi1 ... The user can move placeholders but cannot invent new expressions unless they type a valid identifier already in scope (validate by re-parsing).
- Single and double-quoted literals: keep the original quote style. Escape \ first, then the same quote char, and turn real newlines into \n (and \r, \t, U+2028/U+2029 into escapes). If the new text becomes multi-line and long, optionally offer to convert to a template literal, but only as an explicit user action, because changing the delimiter changes escaping rules and lint/prettier output.
- Preserve existing escapes the user did not change: diff old vs new cooked text, and if a region is unchanged keep its original raw source (for example keep é rather than turning it into é). Simplest approach: if the cooked text is unchanged, emit no edit at all.
- String.raw and other raw tags: do not escape backslashes (raw semantics). Only ` and ${ need care, and since String.raw cannot represent a literal backtick, refuse or fall back if the new text contains a backtick.
- dedent/outdent and other tagged templates: the displayed text is the tag's output, so on write re-indent every new line with the original common indentation (detected from the old raw text), keep the leading newline after the opening backtick and the trailing newline plus indent before the closing backtick, and keep the tag's escaping conventions (dedent treats \` and \${ normally).
- Untagged multi-line templates inside indented code: the indentation is part of the prompt (it is sent to the model). Show it as-is. Do not auto-indent new lines unless the original literal's continuation lines were already at a consistent indent and the user opts in.
- Concatenations and joins: edit only the literal piece the user changed. Never merge or split pieces automatically. If the user adds text at a boundary, put it into the adjacent literal piece; if there is none (expr + expr), refuse rather than inserting new string nodes.
- Shared constants: if the declaration is referenced by more than one LLM call (findReferences), warn before editing, and offer 'edit shared' vs 'inline a copy into this call' (the latter creates a new literal and is an explicit refactor).
- Text and JSON files: for ?raw/.md/.txt, write the whole file with the original encoding, BOM and trailing-newline state preserved. For JSON, edit only the value span with JSON escaping (jsonc-parser modify + applyEdits keeps formatting and comments).
- After every edit, re-parse the modified file and verify (a) no new syntax errors, (b) the same number and order of LLM call sites, (c) the cooked value of the edited literal equals the user's text. Optionally run the repo's prettier/eslint --fix only if the repo already has it configured, and show the git diff before committing.
- Offsets: the TS compiler API, Babel and oxc (recent versions) give UTF-16 indexes that match JS string slicing. tree-sitter gives UTF-8 byte offsets. Always normalize before splicing and test with emoji and non-Latin prompts.

**Existing detectors to reuse:**

- CodeQL 2.26.0 (July 2026) js/system-prompt-injection (javascript/ql/src/Security/CWE-1427/SystemPromptInjection.ql) models system-prompt sinks for the OpenAI, Anthropic and Google GenAI JS SDKs. The source is not embeddable (license), but its models-as-data sink list is a good checklist of SDK call shapes.
- overllm (PyPI) is reported to detect OpenAI/Anthropic/Vercel AI SDK calls in Node code and LangChain-style chains, but it is a Python tool. I could not read its page (fetch failed), so this is unverified. Use it as a reference only.
- SecureAI-Scan (OWASP GenAI solutions listing) is an MIT, offline scanner for TS/JS/Python that finds prompts and LLM calls for security. It could be mined for patterns. Unverified depth.
- llm-audit (Javierlozo/llm-audit) is a proposed Semgrep rule pack for TS/JS LLM apps. Its brief says Semgrep's official p/ai-best-practices has no JS/TS rules. Its release status is unconfirmed.
- LLM observability auto-instrumentation lists (OpenLLMetry/Traceloop instrumentations for JS, Langfuse/Helicone integrations, OpenTelemetry GenAI semantic conventions) are runtime, not static, but their per-library lists of patched methods are a good inventory of which methods to treat as LLM calls.
- Conclusion: no reusable, embeddable, maintained static detector exists that extracts prompt text plus editable spans for JS/TS. Build your own rule table (about 30 call shapes) on top of the parser, and treat the projects above as checklists.

**Risks:**

- Prompts that are not statically known (DB/remote prompt registries, hub.pull, env vars, user-supplied system prompts, i18n lookups) need clear 'runtime' markers or users will think the scanner missed them.
- Wrappers: most real codebases wrap the SDK (callLLM(prompt), an llm.ts helper). Detection must follow calls into local wrapper functions and treat their parameters as prompt slots. This is the main precision/recall challenge and where Claude-assisted mapping helps.
- Fast API churn: Vercel AI SDK (v4 to v5 to v6 renamed fields, e.g. CoreMessage to ModelMessage and Agent system vs instructions), LlamaIndex.TS (OpenAIAgent to agent() in @llamaindex/workflow), LangChain (createReactAgent prompt/stateModifier to createAgent systemPrompt), and Mastra. The rule table must be data-driven and versioned.
- Template DSL braces (LangChain {var}, mustache {{var}}) look like your {placeholder} display syntax. Use a distinct visual chip for code expressions vs template variables, or users will create broken prompts.
- Editing a shared constant silently changes other workflows' prompts.
- UTF-8 vs UTF-16 offset mismatch with tree-sitter (and older oxc/SWC) corrupts files containing non-ASCII. SWC's global span offset bug is a similar trap.
- TypeScript compiler API memory use on big monorepos (hundreds of MB to GB). Run the scanner in a utilityProcess/worker and load per-project.
- Native modules (oxc, ast-grep) need per-platform packaging and asarUnpack in Electron and can trip antivirus (Avast was already an issue on this PC). Pure-JS/WASM choices avoid that.
- TS 7 (native Go compiler) shifts the ecosystem. The JS compiler API in TypeScript 5.x/6.x keeps working, but long-term API support should be watched.
- Some detector sources (overllm, SecureAI-Scan, llm-audit, some CodeQL details) were only seen via search snippets or secondary blogs and were not verified.

## Why other tools make people move prompts out of their code (research, 2026-10-16)

Two agents read what the vendors and code-first tools say themselves, with sources. The owner asked: "why do other companies force people to put prompt in their files and not just leave it in how it is?"

### Prompt registries (Langfuse, PromptLayer, Braintrust, LangSmith, Agenta, Vellum, Portkey, Humanloop)

Across the vendors, one reason comes up again and again: changing a prompt should not need a code deploy or an engineer. Langfuse, PromptLayer, Braintrust, LangSmith, Agenta and Vellum all say that once a prompt lives in their registry and the app fetches it by name and label at runtime, a product manager or domain expert can edit it in a web UI and it goes live immediately. Moving a label (production, staging, LATEST) then becomes how you release or roll back. Secondary reasons: - One place to see every prompt (Portkey, Agenta). - Clearer cause and effect, because prompt changes aren't bundled with unrelated code (Braintrust). - Tracing and evals linked to each version (Braintrust). Most vendors don't state the costs. Their own docs and actions show them: - **Runtime dependency.** Langfuse answers it with an SDK cache (60-second TTL) and an optional fallback prompt kept in code. - **Two sources of truth.** Langfuse says its own version history stays the source of truth and the Git mirror is only a one-way copy. Braintrust lists "keep prompt changes in code and UI in sync" as a requirement. - **Edits that skip code review.** Braintrust UI edits go live without a redeploy. Vellum needed a separate reviewer feature, because tags can be moved in the app. - **Lock-in and forced migration.** Humanloop shut down on 2025-09-08 after its team joined Anthropic; customers had to export their prompts. Humanloop was the most open about the trade-off. Its docs list keeping prompts in code as giving a "point-in-time snapshot of both code and prompts" and keeping existing CI/CD. The main downside it gives is that domain experts find it harder to collaborate. This matches the case for Recaller Code: keep code-first's snapshot and review, and remove the collaboration and visibility pain with a visual board and in-place editing.

**Reasons they give:**

- Ship prompt changes without a code deploy, and let non-engineers do it (Langfuse): "non-technical team members update them directly in the UI while your application automatically fetches the latest version"; "prompt updates deploy instantly, without needing to involve engineering or triggering a deployment." Otherwise a text change can take "hours or days of waiting". <https://langfuse.com/docs/prompt-management/overview>
- Split the roles: PMs and domain experts work on prompts, engineers handle deploys (Langfuse): "Product managers and domain experts iterate on prompts, while engineers manage deployments." <https://langfuse.com/docs/prompt-management/overview>
- Says the registry adds no latency, because the SDK caches prompts (Langfuse): "Langfuse Prompt Management adds no latency to your application"; "Prompts are cached client-side by the SDK" <https://langfuse.com/docs/prompt-management/overview>
- Deploy prompt versions without code changes; review prompts without code diffs; organise them outside the codebase (PromptLayer): "Deploy the right prompt version in production without code changes"; share prompts "for review and collaboration without sending code diffs around"; "organize them outside the codebase" <https://docs.promptlayer.com/features/prompt-registry/overview>
- Escape the deploy cycle, and stop prompt changes being bundled with unrelated code (Braintrust): "Each prompt update requires a full deployment cycle and is often bundled with unrelated code changes"; "Prompt updates become operational changes that skip full code deployments"; rollback "does not require debugging or redeploying code" <https://www.braintrust.dev/articles/what-is-prompt-management>
- Let PMs and domain experts contribute in one shared interface (Braintrust): "Effective prompt management enables all these roles to contribute without bottlenecks"; a "single interface without context switching" <https://www.braintrust.dev/articles/what-is-prompt-management>
- Link traces to the prompt version that produced them, which works only for prompts loaded from Braintrust (Braintrust): Docs: prompt.build() links traces to the origin prompt; if prompts are not loaded from Braintrust, native linking isn't available, so you log the version as custom metadata instead. <https://braintrust.dev/docs/kb/link-prompt-versions-to-traces-from-code>
- Swap the running version by moving a tag, with no code edit (LangSmith (LangChain)): "you can update which version is being used without modifying the code itself"; "Tags provide a stable way to reference specific versions of your prompts in code"; code calls client.pull_prompt("joke-generator:production") <https://docs.langchain.com/langsmith/manage-prompts>
- Update prompts from the web UI without changing code; see every prompt in one place (Agenta): The integration guide says you can update prompts directly from the web interface without modifying your code each time. The registry launch post targeted "not being able to see all your prompts in one place" and added version comparison and one-click rollback. <https://docs.agenta.ai/prompt-management/integration/how-to-integrate-with-agenta>
- Promote and release prompt versions with release tags, with no redeploy (Vellum): API calls without a release tag get LATEST; custom tags "can be moved by authorized users directly within the Vellum app"; promotion to Staging or Production needs "no need to manually redeploy" <https://docs.vellum.ai/product/deployments/release-tags>
- One central library of prompts for the whole team, referenced by ID (Portkey): "A central location for all your prompt templates"; prompt IDs are used to "reference them in your applications via the Prompt API" <https://portkey.ai/docs/product/prompt-engineering-studio/prompt-library>
- Iterate faster and work more easily with subject-matter experts (the UI-first approach) (Humanloop (archived docs)): UI-first: "Faster iteration which can be decoupled from code releases"; "Easier collaboration with subject matter experts". Code-first is "Tightly coupled to code releases, means slower iteration". <https://humanloop.com/docs/explanation/integrating-humanloop>

**What it costs users:**

- Runtime dependency on the vendor's API: you need caching, pre-fetching and a fallback prompt in code to be fully available: Langfuse: on first use "the prompt is fetched from the API"; the default cache TTL is 60 seconds; "a fallback prompt can be used to ensure 100% availability" when the cache is empty and the API is unreachable. That fallback is a second copy of the prompt in your code. <https://langfuse.com/docs/prompt-management/features/caching>
- Two sources of truth: Git becomes a downstream mirror, and the vendor's store is authoritative: Langfuse: "The Langfuse version history remains the deployment source of truth; the Git mirror adds repo-native review tooling and a backup." Sync is a webhook server that commits each new Langfuse version to the repo. Rollback is done "in the Langfuse UI". <https://langfuse.com/docs/prompt-management/features/github-integration>
- The code and UI copies have to be kept in sync: Braintrust's article lists the requirement "Keep prompt changes in code and UI in sync" and admits no other downsides. Braintrust's KB notes there's no webhook on every prompt change, and its handler doesn't sync removals. <https://www.braintrust.dev/articles/what-is-prompt-management>
- Prompt changes go live without the code's pull request review; vendors had to build separate approval features: Braintrust: saving a UI edit makes it live right away unless you pin a version or environment. Vellum: floating tags can be moved by users in the app, so it added "protected" tags that need a reviewer's approval, outside Git. <https://docs.vellum.ai/product/deployments/release-reviews>
- Lose the point-in-time snapshot of code and prompts, and your existing CI/CD: Humanloop lists these as code-first advantages, so moving prompts out loses them: "Maintains a point-in-time snapshot of both code and prompts"; "Maintains your existing CI/CD practices" <https://humanloop.com/docs/explanation/integrating-humanloop>
- Lock-in and forced migration if the vendor goes away: Humanloop shut its platform down on 2025-09-08 after its team joined Anthropic. Prompt workflows and API integrations stopped working, and customers had to export through the API. This comes from a W&B migration page, a competitor; I didn't find Humanloop's own notice. <https://wandb.ai/wandb_fc/product-announcements-fc/reports/Humanloop-is-sunsetting-Migrate-to-Weights-Biases-as-an-alternative--VmlldzoxMzk4ODc1Nw>
- Migration work: the code must change to call the vendor SDK by name and label, with a vendor-specific ID: Braintrust's loadPrompt(project, slug, environment/version) uses a decimal SDK ID, while the UI shows a 16-character hex ID. LangSmith uses pull_prompt(name:tag). PromptLayer uses run(prompt_name, prompt_release_label="prod"). <https://www.braintrust.dev/docs/evaluate/prompts/versions>
- Registry-first doesn't fit complex chains: Humanloop on UI-first: "Does not support complex prompt chains or flows" <https://humanloop.com/docs/explanation/integrating-humanloop>

**Other views:**

- Humanloop presented both approaches as a trade-off and supported prompts stored in your own filesystem and version control alongside its platform. Moving prompts out was optional. (Humanloop) <https://humanloop.com/docs/guides/prompts/store-prompts-in-code>
- Braintrust supports code-first too: define prompts in code, push them with the bt CLI, or download them as plain-text files and review the changes in pull requests. (Braintrust) <https://www.braintrust.dev/docs/evaluate/prompts>
- Langfuse and LangSmith offer Git hooks (a repository dispatch or sync webhook, and a commit webhook for "Synchronizing prompts with a GitHub repository"), but they flow from the platform to Git, not the reverse. (Langfuse / LangSmith) <https://docs.langchain.com/langsmith/manage-prompts>
- Langfuse says the runtime risk is small: the cache keeps apps running during outages, a fallback is "rarely necessary", and first-fetch latency is "acceptable". (Langfuse) <https://langfuse.com/docs/prompt-management/features/caching>
- Kedro's third-party Langfuse dataset has a 'local' sync policy, where local files are the source of truth. Some users clearly want the code to stay authoritative. (Kedro (third party)) <https://docs.kedro.org/projects/kedro-datasets/en/stable/api/kedro_datasets_experimental/langfuse.PromptDataset/>

### Code-first file formats (BAML, Dotprompt, Prompty, GitHub .prompt.yml, Promptfoo, blogus)

The code-first tools give the same few reasons for moving prompts into their own formats. A string in code gets no tooling. BAML names type safety, previews, hot-reload and linting, and adds that you can't test a prompt without running the whole app. These tools also treat a prompt as a unit that bundles the text, the model and settings, and test data (Dotprompt, Prompty, .prompt.yml), so it can run from an editor or playground and in any language (Prompty). Non-coders can then edit it in a UI and export it back (Dotprompt, GitHub). And a file can be versioned, locked and diffed so you know which version is live (blogus, Promptfoo). Most of these reasons are about tooling the vendor can build around a file it controls. None of them shows that the prompt itself needs to live outside the code. The costs are documented: - **Adoption:** the blogus author says the move-first step is why prompt tools "never get adopted". Blogus's own fix step still moves prompts into .prompt files. - **Dependencies:** loading prompt files at runtime adds something the app depends on. - **Testing:** a separate layer can't run your app's code, so it can't test prompts together with tools and retrieval (Hamel Husain). - **Formats:** you have to learn a new format, the formats don't work with each other, and they can be dropped. GitHub's docs now say GitHub Models, which defined .prompt.yml, was retired on July 30, 2026. Promptfoo can already take prompts from JS or Python functions, and Opik says prompts can stay in code while syncing to its platform. So leaving prompts in place works. Among developers, Hamel Husain argues for prompts in git, versioned, reviewed and deployed with the app. Hosted-registry vendors (Langfuse, the TDS piece) argue the reverse: every prompt edit becomes a PR, build and deploy, and git shows the diff but not the outcome. For Recaller Code, scanning prompts where they already are (a find-only step like blogus's scan) avoids the move-first barrier. The app would still need to supply what files give these tools: - previews and runs without the full app - one unit showing the text, model and test cases - a clear "which version is live" view - a way for non-coders to edit without touching git I found no Hacker News or Reddit thread specifically on inline strings versus separate prompt files, and the TDS article returned 403, so its points come only from a search summary. The PyPI listing for blogus (Skelf-Research) and the GitHub repo (llmprogram) have different owners; I didn't check which is official.

**Reasons they give:**

- Prompts are functions with logic, not just strings; strings in code are hard to organize, maintain and test (BAML (BoundaryML)): "Prompts are more than just f-strings; they're actual functions with logic" that becomes hard to organize, maintain and test <https://docs.boundaryml.com/home>
- Strings in code get no developer tooling: no type safety, no hot-reload or preview, no linting (BAML (BoundaryML)): Prompts in code lack type safety, hot-reloading or previews, and linting; BAML lets you view and run prompts in the editor with no setup <https://docs.boundaryml.com/home>
- Testing a small prompt change means running the whole app runtime (BAML (BoundaryML)): With Python/Pydantic you have to run your code and set up a Python environment just to test a small prompt change <https://docs.boundaryml.com/home>
- Prompts built from concatenated strings and f-strings became huge; the team wanted prompts in their own files with autocomplete and jump-to-definition; Python/TS SDKs and YAML were 'not sufficient' (BoundaryML CEO (interview) / BoundaryML homepage): Prompts were concatenated strings, f-strings and other massive constructs; they wanted their own files with autocomplete and go-to-definition; SDKs and YAML "were simply not sufficient" <https://cerebralvalley.beehiiv.com/p/boundary-yc-w23-leveling-prompt-management>
- Prompts are code that should be kept apart from app code, with the model and settings bundled into the same file (Dotprompt (Firebase Genkit)): Designed around the premise that "prompts are code"; each file defines the prompt plus the models and parameters it's meant for <https://genkit.dev/docs/dotprompt/>
- People who don't write app code can refine prompts in the Developer UI and export them back (Dotprompt (Firebase Genkit)): Faster iteration: non-coders tune prompts in the Developer UI, then export them back to the project; file-based is "the best developer experience overall" <https://genkit.dev/docs/dotprompt/>
- Portability: one prompt file runs from the editor and from several language runtimes, and endpoints can be switched without touching the prompt (Prompty (Microsoft)): Built to enhance "observability, understandability, and portability"; "Write your prompt once — run it from VS Code or a language runtime"; "switch the endpoint and key at runtime without changing the prompt body"; matched across Python, TS, Rust and C# <https://github.com/microsoft/prompty>
- Prompts kept as files in the repo can be shown in an organized UI, shared with non-technical people, and carry model settings and test data for evals (GitHub Models (.prompt.yml)): Docs say .prompt.yml files hold the model, parameters, messages and sample test data, and can be viewed in an organized UI and shared with non-technical stakeholders. Note: GitHub Models' docs page now says the product was fully retired on July 30, 2026 <https://docs.github.com/en/enterprise-cloud@latest/github-models/use-github-models/storing-prompts-in-github-repositories>
- External files keep things organized and work better for long prompts; inline text is fine for simple cases. Prompts can also come from JS/Python functions, so a prompt can stay in code (Promptfoo): "Store prompts in external files for better organization"; inline text suits basic use cases; supports file://generate_prompt.js and file://x.py:create_prompt <https://www.promptfoo.dev/docs/configuration/prompts/>
- Prompts are dependencies, and inline strings leave you unsure which version is live. blogus first finds prompts where they already are, then its fix step moves them into .prompt files loaded at runtime (blogus (Dipankar Sarkar, DEV post)): "Prompts are dependencies. We just refuse to treat them like it"; a lock with content hashes answers "which version of the summarize prompt is in production"; `fix` replaces the inline string with load_prompt and a .prompt file <https://dev.to/dipankar_sarkar/a-packagelock-for-the-prompts-hiding-in-your-codebase-2hom>

**What it costs users:**

- Having to move prompts first is why prompt-management tools don't get adopted: The blogus author says most prompt tools ask you to move prompts into their system first, and that migration is why they "never get adopted" <https://dev.to/dipankar_sarkar/a-packagelock-for-the-prompts-hiding-in-your-codebase-2hom>
- Moving prompts out adds something the app depends on when it runs: prompt files must ship and load, which is overkill for trivial prompts: Loading prompts with load_prompt is "a fair trade for versioning, but it is a trade"; the lockfile process may be unnecessary for prompts that rarely change <https://dev.to/dipankar_sarkar/a-packagelock-for-the-prompts-hiding-in-your-codebase-2hom>
- A separate prompt layer adds indirection and can't run your app's code, so prompts can't easily be tested together with tools and retrieval: Hamel Husain: tools "risk creating additional layers of indirection" and "are inherently limiting because they can't easily execute your application's code" <https://hamel.dev/blog/posts/evals-faq/how-should-i-version-and-manage-prompts.html>
- You learn and maintain a new language or format (BAML's DSL and Jinja templates, .prompty, .prompt.yml), and the formats don't work with each other: GitHub's docs say .prompt.yml can't handle complex templating or formats like .prompty; BAML prompts use Jinja templating <https://docs.github.com/en/enterprise-cloud@latest/github-models/use-github-models/storing-prompts-in-github-repositories>
- A format can be dropped by its vendor: GitHub Models, which defined .prompt.yml, was retired: The GitHub docs page says GitHub Models was fully retired as of July 30, 2026 <https://docs.github.com/en/github-models/use-github-models/storing-prompts-in-github-repositories>
- Prompts kept only in a third-party dashboard mean you rent rather than own them: Activepieces: prompts in a vendor dashboard mean you're renting your intellectual property (vendor-side post about leaving Vellum) <https://www.activepieces.com/blog/migrating-your-prompt-library-out-of-vellum-with-automation>

**Other views:**

- Keep prompts in git so they're versioned, reviewed and deployed atomically with the application code; non-technical people can use GitHub's web UI. He doesn't say whether that means separate files or inline strings (Hamel Husain) <https://hamel.dev/blog/posts/evals-faq/how-should-i-version-and-manage-prompts.html>
- Against git: product people and non-engineers can't contribute, prompt changes inherit the backend's deploy friction, and git shows the diff but not the outcome (only seen in a search summary; the page returned 403) (Towards Data Science, 'Why your prompts don't belong in git') <https://towardsdatascience.com/why-your-prompts-dont-belong-in-git/>
- With prompts in code, every prompt change is a code change: pull request, review, build, deploy. This is a vendor's argument for its registry (Langfuse workshop) <https://langfuse.com/workshop/learner/03-prompt-management.md>
- Middle ground: a prompt library doesn't stop you keeping the prompt in code; prompts can be versioned in code and synced to the platform (Opik (Comet)) <https://www.comet.com/docs/opik/prompt_engineering/prompt_management>
- A prompt is production code with no type system, no compiler and no stack trace; what you really need is versioning, evaluation and rollback, whatever tool provides them (Arize glossary) <https://arize.com/glossary/prompt-management-system/>
- Once prompts carry logic and return structured data, reusing them leads to copy-paste drift, so they need code-like treatment (codeaholicguy, DEV Community) <https://dev.to/codeaholicguy/prompts-are-becoming-code-but-we-still-treat-them-like-strings-4o1j>
- Developers are split on making prompts part of code review: 49% loved it and 24% hated it (Gergely Orosz poll as reported; this is about coding-agent prompts, not app prompts) (Quesma, DEV Community) <https://dev.to/teamquesma/vibe-coding-needs-git-blame-431m>

## Mockup, second round (2026-10-16)

The owner's feedback on the first four-screen mockup: "i want it to be more usuer friendly and simple, remember the goal is to create a app that can manage your prompts in your code and products seemlessly and easily and organized it and visually see". Three critiques of those screens (a first-time user, the owner's Recaller taste, a radical minimalist) agreed on these changes, which the second mockup uses:

- A first-run screen: one "Open a project folder" button, live progress in plain words, and "Nothing in your code was changed."
- Each prompt appears once, in the order the code runs it. Its stage is a small label on the card ("Cooking · being changed", "Cooked · in review", "Served · live") instead of three stage sections that repeated the same prompt. This changes the earlier stage layout and waits for the owner's OK.
- No separate flow or test pages. The column reads as the flow, and the prompt opens over the board to read, edit, try and send in one place.
- The prompt reads as text you edit, with the values the code fills in as locked green chips. Shared text is tinted and explains itself when clicked.
- One main button, "Send for review". Sending closes the prompt and returns to the board with a toast, like Recaller's "save closes the editor".
- Model, file and line, the code change and past versions sit behind one "Details" disclosure. No branch, commit or PR words on the main surface.
- Scanning is automatic. A newly found workflow appears as a faint column with "Add to board" and "Not now".
- Stage chips use Recaller's stage colours only (white Cooking, Ocean Cooked, sage Served): no amber or brown, no violet. Column headers keep their distinct colours, as the owner's taste requires.
